### 新ツム登録と既存TDKで十分な部分

1. `npm run tsum:new -- newTsum`または`--template=chain`で5ファイルを生成し、`tsums/catalog.js`を自動登録。
2. 定義・専用スキル・演出・画像を編集。capabilitiesと実フック、SL1〜6、対応モードを一致させる。
3. 固有テストを更新し、`tsum:validate`、`test:tdk`、関連する既存回帰を実行。
4. 開発URLで実入力・終了・再試験・通常操作への復帰を確認。

登録のための`game.js`・`config.js`・`ui.js`手編集は不要。保存隔離・通常カタログからの除外も既存機能を使える。標準チェーン追跡、消去ターゲットの除重複、コイン補正、ゲージ回収、補充は既存経路に委譲する。

状態は`session.data`、更新は`onTick`、終了は`onEnd`/`cleanupBySession`、一時盤面状態は`clearBySource`を再利用できる。発動・終了演出の時計/物理停止は既存timing設定、消去中はClearPipelineの個別フラグで指定できる。

ただし`onTick`へ渡るのはgameplayDtであり、独自の時間軸を万能に提供するAPIではない。DOPAの通常更新迂回やPHOTONの固定刻み・時計停止中の進行には既存の個別接続がある。未知のスキルにも共通ファイル変更が必ず0件とは断定しない。

### 最も手間が残る工程

ソース構造から見て、負担が集中するのは**独自仕様を時間・入力・消去の境界に落とし込み、再現テストで固定する工程**。時間順位や人時は未測定。

- どの時計を止め、独自シミュレーション・盤面落下・補充・音声のどれを進めるか決める。
- pointer-upと時間切れが重なる場合に、破棄・確定・最終攻撃のどれを行うか決める。
- 標的を入力時／攻撃時／補充後のどこで確定し、同じ実体への二重報酬を防ぐか決める。
- 既知盤面・入力列・時間刻み・SL・消去受付の成否を固定し、不具合を再現してから修正する。

既存の小さな専用harnessや`makeTdkGame`を利用できるため、これらをすべて新しいテスト言語に置き換える理由はない。`makeTdkGame`のゲーム乱数はseed付きだが、runtime contextの`rng.float`は`Math.random`である。乱数を使う新仕様では入力乱数を明示的に固定し、全面的な決定性があるとは扱わない。

## 5. 物理p95の限定比較

環境: Windows 11 Home 10.0.26200、Node v24.18.1、AMD Ryzen AI 9 HX 375、論理CPU 24。2026-10-15 21:32 JSTごろ。同じホスト・同じNodeで、v1.0=`170c737`、v1.1=`ab66ad3`のソースを取り出して逐次実行した。対象テストの直接依存は`tsumPhysics.js`とNode標準モジュールだけで、TDKやGameはimportしない。

`tsumPhysics.test.mjs`と`tsumPhysics.js`はいずれも両版で同一。コピーのSHA-256も保存。比較はこの物理単独試験に限られ、ゲーム全体の性能比較ではない。

計測条件: 同じ初期配置45体、600step、p95は昇順のindex 570、閾値は`p95 < 4`のまま。明示的な事前warmupはなく、最初のstepも計測に含む。新規Nodeプロセスごとに起動。こちらからの他のテスト・ベンチマークは同時実行しなかった。

まず原本と同じテストを各1回実行し、双方成功した。原本は成功時p95を出力しないため正確な値は取得不可。その後、**使い捨てコピーだけ**に600stepの計測終了後のログを追加し、正確なp95を各3回取得。assertと4ms閾値、物理処理は変更していない。v1.0→v1.1、v1.1→v1.0、v1.0→v1.1と順序を交替した。

| 回 | v1.0 p95 | v1.1 p95 | 結果 |
| --- | ---: | ---: | --- |
| 診断1 | 4.4994ms | 4.4154ms | 双方超過 |
| 診断2 | 3.7362ms | 4.3801ms | v1.1超過 |
| 診断3 | 3.1918ms | 3.3748ms | 双方成功 |

補助観測では最初60stepのp95は5.3373〜7.3872ms、残り540stepは2.9463〜4.4258ms。初期区間の負担は見えるが、同じ盤面を事前にwarmupした比較ではない。JIT・初期接触・sleep移行・外部負荷の影響を分離できず、warmupだけが原因とは言えない。末尾540stepでも超過が残る。合否は全600stepの値で判定し、末尾だけで成功扱いにしていない。

バックグラウンド負荷: `Get-Process`で各試行前後のアクセス可能なCPU累積値を取得。VALORANTのCPU増分は各観測区間で約10.172〜16.359 CPU秒、Chrome・ChatGPT・その他Node等にも増分を確認した。CPU秒は複数コアの合計で、観測区間にはスナップショット処理も含む。百分率・試験プロセスの専有率・p95との因果関係は示さない。外部アプリを停止したり設定を変更したりしていない。

**判断:** 同じ物理コード・同じ単独テストでも合否が変動した。TDK変更による物理実装の退行を示す結果ではなく、外部負荷や起動初期の影響が疑われる。ただし静穏環境、電源状態、温度、CPU周波数、スケジューリングを固定していないため、原因は未特定・未解決。閾値も物理実装も変更しない。今回の切り分けはここで終了する。
